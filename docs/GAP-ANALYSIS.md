# HaneHana 功能差距分析（vs 市面同类产品）

> 日期：2026-07 · 依据：竞品公开文档调研（Playnite / GalgameManager / LunaTranslator）+ 本仓库代码现状核实 + IMPROVEMENT-SPEC §3 对标表
> 结论先行：**HaneHana 的「下载引擎」与「游戏站捕获」已是差异化优势**（Rust 多线程分段 + 校验和，市面 galgame 管理器没有），
> 真正的差距集中在**元数据深度、存档管理、平台导入、批量能力、统计可视化**五块。

---

## 一、现状全景（已核实）

| 模块 | 已有能力 |
|---|---|
| 游戏库 | 文件夹扫描导入（exe/bat/lnk、黑名单排除、异步遍历）、VNDB+Bangumi 双源刮削、封面墙/列表双视图（虚拟化）、分类/标签/搜索（防抖+索引）/排序、一键启动（LE/Magpie 开关已存）、游玩时长统计（进程监控）、移除/打开目录 |
| 下载 | Rust 多线程分段引擎（206 探测、Range 分片、暂停续传、令牌桶限速、MD5/SHA-1/SHA-256 校验）、任务列表（状态过滤/排序/批量操作/总速度）、断点持久化（.part 水位+sidecar） |
| 游戏站 | 内嵌 webview 浏览器 + 聚合搜索（nekogal/gamer520/playzip）+ 镜像解析 + 下载捕获（直链进引擎/需会话交浏览器） |
| 系统 | 托盘常驻、系统通知（完成/失败可配）、自动更新（electron-updater+tag Release）、自定义标题栏、多主题（樱夜/星海/薄荷，三态跟随系统）、自定义背景、限速/代理/UA/并发数设置、防休眠 |
| 交付 | typecheck/build 双绿、e2e 29、cdp_ui 9、cdp_visual 8、cargo test、CI、tag 发版 |

## 二、竞品对标（同类产品在做什么）

| 产品 | 定位 | 与 HaneHana 重叠 | 值得学 |
|---|---|---|---|
| **Playnite** | 通用游戏库（多平台聚合） | 库管理、刮削、时长 | 商店库导入、插件生态、全屏模式、多维筛选 |
| **GalgameManager**（lxl66566） | galgame 管理器（最直接竞品） | 库管理、刮削、时长 | 存档备份/云同步、插件系统、统计报表、异常检测 |
| **LunaTranslator** | galgame 翻译工具（集成思路） | 无（领域不同） | 多工具集成、OCR/翻译挂接入口 |
| Motrix / IDM | 下载器 | 下载引擎 | 已超（HaneHana 引擎≥aria2 能力） |

> 结论：HaneHana 目前是「库 + 下载一体」，GalgameManager 是「库 + 存档一体」。**两边各缺对方的半壁江山。**

## 三、差距清单（按价值分级）

### 🔴 高价值缺口（建议优先做）

| # | 能力 | 市面对标 | HaneHana 现状 | 价值理由 |
|---|---|---|---|---|
| G1 | **存档备份/恢复/云同步** | GalgameManager：本地+WebDAV/S3、定时上传、启动拉取、事务回滚 | 无 | galgame 玩家最怕坏档；这是 GalgameManager 核心卖点，也是 HaneHana 与它正面竞争时最大的短板 |
| G2 | **插件/工具集成系统** | Playnite 插件生态；GalgameManager 插件（LE/翻译/加速/自动上传） | LE/Magpie 仅存开关，未实际集成 | 让 LE/Magpie/翻译工具/OCR 以插件挂接，避免核心膨胀；当前「启动包装」只有开关没有行为 |
| G3 | **元数据深度扩展** | VNDB v2 结构化字段（角色/画师/开发商/发行商/系列/时长/别名/截图） | 仅 title/desc/date/rating/tags/cover | 选游戏时「看画师/看系列/看时长」是 galgame 玩家的核心决策路径；现在库里根本存不下 |
| G4 | **平台/商店库导入** | Playnite：Steam/Epic/GOG 已购导入 | 仅本地文件夹扫描 | 让「已买没下」的游戏也进库；扫描导入只能覆盖「已下载」 |
| G5 | **统计报表可视化** | GalgameManager：每日时长+数据展示+封面取色 | 有 playMs/lastPlayed 字段但无任何报表 UI | 数据已经躺在 games.json 里，只差一层 UI；「本月玩了多少 galgame」是社交分享刚需 |

### 🟡 中价值缺口

| # | 能力 | 市面对标 | 现状 | 价值 |

## 四、差异化定位再确认

HaneHana 的独特位置：**「找到 → 下下来 → 入库 → 启动 → 记录时长」一个窗口内闭环**，市面没有第二个产品做到这一点：

- Playnite 有库没有下载；IDM/Motrix 有下载没有库；GalgameManager 有库+存档但没有内嵌游戏站捕获；
- **游戏站捕获 + Rust 引擎**是 HaneHana 的护城河，差距分析里的建议都不该稀释它。

## 五、建议的实现顺序（如果要做）

1. **统计报表**（G5）——数据已有，纯前端，一周内可交付，立刻让库「活」起来
2. **收藏夹/愿望单**（G9）+ **批量编辑**（G6）——库管理体验补课，改动可控
3. **元数据深度**（G3）——扩 Game 字段 + 刮削填充（VNDB v2 已有这些字段，改动主要是存储与 UI）
4. **手动编辑**（G7）——配合 G3，字段多起来更需要手改兜底
5. **插件系统**（G2）/ **存档同步**（G1）——工作量最大，需要单独设计（存档同步尤其要设计冲突策略）
6. 其余按价值/成本比取舍

> 注：游戏站深化（更多站点/订阅源）、LE/Magpie 实际集成、浏览器扩展投递，属「扩展能力」而非「缺口补课」，与上面清单正交，可并行推进。
